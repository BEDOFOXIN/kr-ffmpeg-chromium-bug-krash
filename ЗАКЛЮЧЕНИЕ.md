# Заключение: WebM крашит Chromium/Discord — полный разбор

Дата: 17.10.2026. Итог всей работы над `cat.webm` и последующих репро-тестов.

---

## 1. Итог одной строкой

**Валидный WebM с Vorbis-аудио: `CodecDelay = +128` сэмплов + отрицательный
`DiscardPadding` (−1025 сэмплов) на полноразмерном блоке в середине потока.
ffmpeg читает без ошибок, а Chromium/Discord падает на release-`CHECK_LE` в
`AudioDiscardHelper::ProcessBuffers()`: перенос 129 сэмплов > допустимые 128.**

Баг **в Chromium** (не в ffmpeg). Это **не единичный случай**: воспроизведён на
5+ независимых файлах разного содержания и разрешения, а также с `DiscardPadding`
на 200 сэмплов переноса (1096 сэмплов).

## 2. Точные условия краша (все обязательны)

| # | Условие | Значение | Зачем нужно |
|---|---------|----------|-------------|
| 1 | Аудио-кодек **Vorbis** | `A_VORBIS` | Opus **не** крашит |
| 2 | `CodecDelay` на аудио-`TrackEntry` | +2 666 667 нс = +128 сэмплов @48кГц | сдвиг начала потока |
| 3 | `DiscardPadding` **отрицательный** | −21 354 167 нс = −1025 сэмплов | валидное signed-поле, означает «отбросить с начала блока» |
| 4 | Блок обёрнут в `BlockGroup` | `BlockGroup` → `Block` + `DiscardPadding` | контейнер аномалии |
| 5 | Блок **в середине потока** | после него есть ещё аудио-блоки | на последнем блоке краша нет (эмпирически) |
| 6 | Блок **крупный** (1024 сэмпла, шаг ~21 мс) | не микро-блок (128 сэмплов, ~3 мс) | на микро-блоках overlap не срабатывает |

Если убрать любое из условий — краша нет. Это доказано матрицей бисекции.

## 4. Все подводные камни (важно для репро и отчёта)

### 4.1. Индекс (`SeekHead`/`Cues`) — ложный след
Первоначально казалось, что виноват вырезанный индекс перемотки. **Это не так.**
Хирургическое восстановление индекса (без изменения всего остального) не убирает
краш. Индекс — отдельная аномалия `cat.webm`, к крашу отношения не имеет.

### 4.2. `-c copy` молча «чинит» файл
`ffmpeg -c copy` (8.x) переписывает `BlockGroup`+`DiscardPadding` в обычный
`SimpleBlock`. Поэтому:
- **нельзя** использовать `-c copy` для подготовки broken-файла;
- `-c copy` — это одновременно «контрольный фикс» (доказывает, что триггер исчезает);
- репро обязан применять инжект **после** всех перемуксов.

### 4.3. `CodecDelay` не создаётся ffmpeg 8.x
Современный ffmpeg (8.x) не пишет `CodecDelay` для Vorbis. Поэтому чистый файл,
созданный текущим ffmpeg, не крашит — нужно **добавить** `CodecDelay` руками
(`mkv_add_codecdelay.py`), эмулируя ffmpeg 7.1.

### 4.4. Позиция блока: только середина потока
Отрицательный `DiscardPadding` по спецификации означает «отбросить N сэмплов с начала
блока». Эмпирически краш возникает только когда такой блок стоит **в середине**
потока: если блок последний — краша нет. Точный механизм внутри Chromium не
подтверждён (гипотеза — спотыкается при расчёте длительности/таймстемпа).

### 4.5. Размер блока: только крупные (1024 сэмпла)
Vorbis чередует крупные (1024 сэмпла, ~21 мс) и микро (128 сэмплов, ~3 мс) блоки.
Краш — только на крупных. У `wood7`/`wood8` первый инжект случайно попал в микро-
зону и не крашил; после выбора крупных блоков — крашит. Флаг `--min-step-ms 15`
в инжекторе решает это автоматически.

### 4.5.1. Диапазон значений `DiscardPadding`, вызывающих краш
Краш — не «при любом большом отрицательном», а **в точном окне**. При
`decoder_delay_ = 128` и блоке 1024 сэмпла:

```
carry = DiscardPadding − (1024 − 128) = DiscardPadding − 896
краш ⟺ 128 < carry < 1024 ⟺ 1025 ≤ DiscardPadding ≤ 1919 (сэмплов)
```

| padding (сэмплы) | carry | исход |
|---|---|---|
| 1024 | 128 | не крашит (`CHECK_LE(128,128)` проходит) |
| 1025 | 129 | **крашит** (минимальное) |
| 1096 | 200 | **крашит** |
| 1500 | 604 | **крашит** |
| 1919 | 1023 | **крашит** (максимальное) |
| 1920 | 1024 | не крашит (буфер съедается → `return false`) |
| 2000 | 1104 | не крашит |

Две границы заданы двумя разными ранними выходами в `ProcessBuffers()`:
1. **Нижняя** (carry ≤ 128): `CHECK_LE` допускает равенство (`≤`, а не `<`),
   `discard_start = 128 − 128 = 0` валидно.
2. **Верхняя** (carry ≥ 1024): до ветки с `CHECK_LE` срабатывает
   `min(carry, 1024) == decoded_frames` → весь буфер отбрасывается и
   `return false`, `CHECK_LE` не достигается.

Обобщённо: **краш тогда и только тогда, когда
`decoder_delay_ < carry < block_size`** — перенос превышает задержку (нарушает
`CHECK_LE`), но меньше целого блока (не уходит в ранний `return false`).

### 4.6. Vorbis-специфичность
Тот же инжект на Opus не даёт краша, потому что для Opus `codec_delay` в
`ResetTimestampState()` принудительно обнуляется (`config.codec() == kOpus ? 0 :
config.codec_delay()`), и путь `decoder_delay_ > 0` с `CHECK_LE` не достигается.
Баг — **в Chromium (AudioDiscardHelper)**, а не в ffmpeg и не в Matroska.

### 4.7. Контейнер: Discord берёт только DocType `webm`
`ffmpeg -c copy` из `.ogv` в `.mkv` даёт DocType `matroska` — Discord такие не
проигрывает. Нужен именно DocType `webm`. Проверка — первый байт EBML-заголовка
содержит строку `webm`.

### 4.8. Видео-кодек: Chrome/Discord не играют Theora
Ранние образцы с Wikimedia Commons были Theora+Vorbis (`.ogv`). Chrome **не
поддерживает Theora вообще** — файлы не открывались даже без инжекта. Для теста
нужно видео **VP8/VP9/AV1** (аудио Vorbis можно оставить). Theora → VP8
перекодировать через `-c:v libvpx -c:a copy`.

### 4.9. EBML: `0xFF` — служебный маркер «unknown size»
Размер элемента, равный 127 байт, кодируется одним байтом `0xFF`, который в EBML
означает «размер неизвестен» (зарезервированное значение). Наивный кодировщик
размера выдавал его — и файл ломался уже на уровне контейнера (`Unknown-sized
element`). Исправлено: кодировщик пропускает all-ones значение и берёт следующий
байт. Проявляется на блоках размером ровно 127/16383/… байт.

### 4.10. `DiscardPadding` — **signed**, а не unsigned (моя ошибка исправлена)
Изначально я ошибочно считал `DiscardPadding` беззнаковым полем и строил на этом
всю аргументацию «мюксер пишет невалидный output». **Это неверно.** По спецификации
Matroska `DiscardPadding` — `type="integer"` (знаковое), и отрицательные значения
валидны: они означают «отбросить N сэмплов с **начала** блока». Подтвердил
мейнтейнер ffmpeg James Almer в тикете #25132.

Следствие: **бага в ffmpeg нет**. Весь баг — на стороне Chromium, который не умеет
обрабатывать отрицательный `DiscardPadding`. Формулировки «нарушение спецификации
мюксером» неверны и удалены из документов.

## 6. Минимальный репро (стабильный)

```bash
# 1. Чистый WebM (VP8/Vorbis, 6 с)
ffmpeg -y -f lavfi -i "testsrc2=size=320x240:rate=30" \
       -f lavfi -i "sine=frequency=440:sample_rate=48000" \
       -t 6 -c:v libvpx -b:v 500k -c:a libvorbis clean.webm

# 2. Добавить CodecDelay (эмуляция ffmpeg 7.1)
python mkv_add_codecdelay.py clean.webm step2.webm

# 3. Инжект: 3 крупных аудио-блока в середине потока
python mkv_inject_crash.py step2.webm crash.webm --start-index 200 --count 3 --min-step-ms 15

# 4. Проверка: ffmpeg НЕ видит ошибок (это норма, баг невидим для ffmpeg)
ffmpeg -v error -i crash.webm -f null -    # пусто, exit 0

# 5. Контроль: перемукс ffmpeg 8.x чинит файл
ffmpeg -i crash.webm -c copy fixed.webm    # BlockGroup->SimpleBlock, DiscardPadding убран
```

## 7. Предлагаемые правки

### Chromium — `AudioDiscardHelper::ProcessBuffers()` (точное место)
Проблема: фронт-отбрасывание (`DiscardPadding.first`) накапливает перенос
`discard_frames_`, который **превышает** `decoder_delay_`, и на следующем блоке
`frames_discarded_so_far > decoder_delay_` роняет `CHECK_LE`. Варианты:
1. Не допускать `discard_start` в отрицательную зону: вместо `CHECK_LE` корректно
   разносить перенос по нескольким буферам.
2. Игнорировать/клампить отрицательный `DiscardPadding` при `decoder_delay_ > 0`
   до тех пор, пока не будет корректной поддержки переноса.

### Chromium — MSE-путь (`webm_cluster_parser.cc`)
Отрицательный `DiscardPadding` сейчас молча отбрасывается (TODO crbug/969195).
Отдельная правка корректности, не связанная с этим крашем.

### ffmpeg (бага нет — правка не требуется)
`DiscardPadding` записывается корректно (signed, по спецификации). Отрицательные
значения — валидная и ожидаемая конструкция. Изменения в ffmpeg не нужны.

## 8. Первопричина на уровне исходников Chromium

Точное место: `media/base/audio_discard_helper.cc` →
`AudioDiscardHelper::ProcessBuffers()`, ветка фронт-отбрасывания:

```cpp
size_t discard_start = decoder_delay_;
if (decoder_delay_ > 0) {
  const size_t frames_discarded_so_far =
      original_frame_count - decoded_buffer->frame_count();
  CHECK_LE(frames_discarded_so_far, decoder_delay_);   // ← падение
  discard_start -= frames_discarded_so_far;
}
```

Порядок операций (проверен по коду):
1. `original_frame_count` захватывается **до** трима.
2. Сначала применяется накопленный перенос `discard_frames_` (TrimStart).
3. Потом в ветке front-discard вычисляется `frames_discarded_so_far`.
4. `frames_discarded_so_far` включает только что применённый перенос.

Расчёт для `DiscardPadding = 1025` сэмплов, блок 1024 сэмпла, `decoder_delay_ = 128`:
- блок A: перенос `1025 − (1024 − 128) = 129`;
- блок B: `frames_discarded_so_far = 129 > decoder_delay_ = 128` → `CHECK_LE` FAIL.

**Падает на 2-м подряд** блоке с отрицательным `DiscardPadding` (третий недостижим).

Для `DiscardPadding = 1096` сэмплов перенос = `1096 − 896 = 200`, тот же краш
(`200 > 128`) — подтверждено файлом `crash_200.webm`.

### Два пути демуксинга (важный нюанс)
- **Path A — FFmpeg-demuxer** (`ffmpeg_common.cc`): отрицательный `DiscardPadding`
  попадает в `.first` (front) → `CHECK_LE` **достижим**. Вероятно, это путь Discord.
- **Path B — MSE** (`webm_cluster_parser.cc`): значение уходит в `.second` (end)
  со знаком, в release молча игнорируется (TODO crbug/969195). Здесь `CHECK_LE`
  **не достигается** — но это не доказывает безопасность всего MSE-сценария.

### Гипотеза регрессии (не доказана)
Коммит `f9f8b3590d3f` («Improve trimming of silence from vorbis audio»,
2026-05-05) переключил Vorbis `delayed_discard=true → false`, после чего
`decoder_delay_ > 0` стал сочетаться с фронт-отбрасыванием и сделал `CHECK_LE`
достижимым. Изменение кода подтверждено статически; то, что оно **ввело**
регрессию — гипотеза (нужна сравнительная сборка до/после).
