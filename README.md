# WebM баг: отрицательный `DiscardPadding` + `CodecDelay` крашат Chromium/Discord

## Что это

Есть класс WebM-файлов, которые **ffmpeg декодирует без единой ошибки**, но на
которых **падает Chromium** (в том числе десктопный клиент Discord).

Причина — сочетание двух аномалий в аудио-дорожке (Vorbis):

1. На аудио-`TrackEntry` стоит `CodecDelay` — положительный, `2 666 667 нс`
   (= 128 сэмплов @48 кГц). Пишет ffmpeg 7.1.
2. Один или несколько аудио-блоков **в середине потока** обёрнуты в `BlockGroup`
   и несут **отрицательный** `DiscardPadding` — `−21 354 167 нс` (= −1025 сэмплов
   @48 кГц). По спецификации Matroska `DiscardPadding` — unsigned, отрицательное
   значение некорректно.

Оба условия обязательны (см. матрицу ниже). Контент и разрешение роли не играют:
крашит и синус на 320×240, и шум на 720×1280.

## Точное условие краша

| № | Условие | Где | Байты / значение |
|---|---------|-----|------------------|
| 1 | `CodecDelay` | `Tracks` → `TrackEntry` (type 2) | `56 aa 83 28 b0 ab` = 2 666 667 нс |
| 2 | `DiscardPadding` < 0 | `Cluster` → `BlockGroup` → `DiscardPadding` (0x75A2) | −21 354 167 нс (−1025 сэмплов) или −20 833 нс (−1 сэмпл) |

Дополнительно: `BlockGroup` должен стоять **не последним** в потоке — после него
должен быть ещё аудио-блок. Отрицательный `DiscardPadding` «растягивает» блок назад
и наезжает на следующий; если блок последний, наезжать не на что и краша нет.

## Откуда взялось

- **ffmpeg 7.1** (`Lavf61.7.100`) писал эти `BlockGroup` + отрицательный
  `DiscardPadding` + `CodecDelay`.
- **ffmpeg 8.x** (`Lavf62.3.100`) при перемуксе переписывает блоки в обычный
  `SimpleBlock` без `DiscardPadding` — краш исчезает.

## Как собрать ломаный файл (репро)

Нужны три скрипта (в этой папке): `ebml_break.py`, `mkv_add_codecdelay.py`,
`mkv_inject_crash.py`. Зависимостей кроме Python 3 нет.

```bash
# 1. Чистый WebM — контент не важен, подойдёт любой VP8/Vorbis.
ffmpeg -y -f lavfi -i "testsrc2=size=320x240:rate=30" \
       -f lavfi -i "sine=frequency=440:sample_rate=48000" \
       -t 6 -c:v libvpx -b:v 500k -c:a libvorbis clean.webm

# 2. Добавляем CodecDelay на аудио-трек (как делал ffmpeg 7.1).
python mkv_add_codecdelay.py clean.webm step2.webm

# 3. Оборачиваем 3 аудио-блока в середине потока в BlockGroup
#    с отрицательным DiscardPadding (-1025 сэмплов).
python mkv_inject_crash.py step2.webm crash.webm --start-index 200 --count 3
```

Итог — `crash.webm`:

- `ffmpeg -v error -i crash.webm -f null -` → **0 ошибок**;
- Chromium / Discord → **краш**.

Полезные флаги `mkv_inject_crash.py`:

| Флаг | Назначение | По умолчанию |
|------|-----------|--------------|
| `--count N` | сколько аудио-блоков обернуть | `3` |
| `--start-index N` | с какого аудио-блока начинать (0-based) | последние `N` |
| `--discard-padding NS` | значение `DiscardPadding` в наносекундах | `-21354167` |
| `--positive` | сделать `DiscardPadding` положительным (контроль) | — |
| `--keep-keyframe-flag` | не сбрасывать флаг keyframe у блока | — |

> Важно: для воспроизведения краша нужно, чтобы выбранные блоки были **в середине**
> потока (не в конце). Отсюда `--start-index 200 --count 3`.

## Как примерно фиксить (в ffmpeg)

Корень — в мюксере/демуксe Matroska (`libavformat/matroska*.c`).

1. **Мюксер**: `DiscardPadding` по спецификации unsigned, поэтому отрицательные
   значения нужно зажимать к `0` перед записью. Искать место, где
   `MATROSKA_ID_DISCARDPADDING` формируется из длительности пакета.
2. **Демуксер**: при чтении отрицательного `DiscardPadding` игнорировать его и
   вывести предупреждение (сейчас молча пропускается).
3. **Расследовать источник**: понять, почему пайплайн 7.1 выдавал
   `DiscardPadding = −1025` / `−1` сэмпл именно при наличии `CodecDelay = +128`
   сэмплов (вероятно, вычитание задержки из длительности последних блоков).

Минимальная правка, снимающая краш у уже существующих файлов, — пункт 2
(демуксер не должен допускать отрицательный `DiscardPadding` до плеера).

## Матрица бисекции

| Файл | Изменение | Краш |
|------|-----------|------|
| `cat.webm` | оригинал (7.1) | да |
| + только `SeekHead`/`Cues` | индекс ни при чём | да |
| только Info/Tracks/Tags | не метаданные | да |
| только флаг блока 0x00→0x80 | не флаг | да |
| `BlockGroup` без `DiscardPadding` | padding виноват | нет |
| `BlockGroup`→`SimpleBlock`, padding убран | — | нет |
| без `CodecDelay`, с отриц. `DiscardPadding` | — | нет |
| с `CodecDelay`, без `DiscardPadding` | — | нет |
| с `CodecDelay`, с отриц. `DiscardPadding` | **триггер** | **да** |
