# WebM: отрицательный `DiscardPadding` + `CodecDelay` крашат Chromium/Discord

## Что это

Есть класс WebM-файлов, которые **ffmpeg декодирует без единой ошибки**, но на
которых **падает Chromium** (в том числе десктопный клиент Discord).

Причина — валидная конструкция Matroska, которую Chromium неверно обрабатывает:

1. На аудио-`TrackEntry` стоит `CodecDelay` — положительный, `2 666 667 нс`
   (= 128 сэмплов @48 кГц). Пишет ffmpeg 7.x.
2. Один или несколько аудио-блоков **в середине потока** обёрнуты в `BlockGroup`
   и несут **отрицательный** `DiscardPadding` — `−21 354 167 нс` (= −1025 сэмплов
   @48 кГц).

`DiscardPadding` — **знаковое** целое по спецификации Matroska
(`type="integer"`). Отрицательные значения **валидны** и означают «отбросить
столько сэмплов с начала блока». Chromium на них падает вместо того, чтобы
учесть. **Это баг Chromium, а не ffmpeg** (подтвердил мейнтейнер ffmpeg James
Almer — <https://code.ffmpeg.org/FFmpeg/FFmpeg/issues/25132>).

Условия краша перечислены ниже; контент и разрешение роли не играют: крашит и
синус на 320×240, и шум на 720×1280.

## Точное условие краша

| № | Условие | Значение |
|---|---------|----------|
| 1 | Аудио-кодек | **Vorbis** (Opus не крашит) |
| 2 | `CodecDelay` | +2 666 667 нс = +128 сэмплов @48 кГц |
| 3 | `DiscardPadding` отрицательный | −21 354 167 нс (−1025 сэмплов) |
| 4 | Обёрнут в `BlockGroup` | `BlockGroup` → `Block` + `DiscardPadding` |
| 5 | В середине потока | после блока есть ещё аудио-блок |
| 6 | Полноразмерный блок | 1024 сэмпла (~21 мс), не микро-блок 128 сэмплов |

Все шесть обязательны: убери любое — краша нет (см. матрицу ниже).

## Откуда взялось

- **ffmpeg 7.1** (`Lavf61.7.100`) писал эти `BlockGroup` + отрицательный
  `DiscardPadding` + `CodecDelay`.
- **ffmpeg 8.x** (`Lavf62.3.100`) при перемуксе переписывает блоки в обычный
  `SimpleBlock` без `DiscardPadding` — краш исчезает.

## Как собрать ломаный файл (репро)

Нужны три скрипта (в этой папке): `ebml_break.py`, `mkv_add_codecdelay.py`,
`mkv_inject_crash.py`. Зависимостей кроме Python 3 нет.

```bash
# 1. Чистый WebM — контент не важен, подойдёт любой VP8/Vorbis.
ffmpeg -y -f lavfi -i "testsrc2=size=320x240:rate=30" \
       -f lavfi -i "sine=frequency=440:sample_rate=48000" \
       -t 6 -c:v libvpx -b:v 500k -c:a libvorbis clean.webm

# 2. Добавляем CodecDelay на аудио-трек (как делал ffmpeg 7.1).
python mkv_add_codecdelay.py clean.webm step2.webm

# 3. Оборачиваем 3 полноразмерных (1024 сэмпла) аудио-блока в середине потока
#    в BlockGroup с отрицательным DiscardPadding (-1025 сэмплов).
python mkv_inject_crash.py step2.webm crash.webm --start-index 200 --count 3 --min-step-ms 15
```

Итог — `crash.webm`:

- `ffmpeg -v error -i crash.webm -f null -` → **0 ошибок**;
- Chromium / Discord → **краш**.

Полезные флаги `mkv_inject_crash.py`:

| Флаг | Назначение | По умолчанию |
|------|-----------|--------------|
| `--count N` | сколько аудио-блоков обернуть | `3` |
| `--start-index N` | с какого аудио-блока начинать (0-based) | последние `N` |
| `--min-step-ms N` | брать только блоки с шагом ≥ N мс (отсев микро-блоков) | `0` |
| `--discard-padding NS` | значение `DiscardPadding` в наносекундах | `-21354167` |
| `--positive` | сделать `DiscardPadding` положительным (контроль) | — |
| `--keep-keyframe-flag` | не сбрасывать флаг keyframe у блока | — |

> Важно: для воспроизведения краша блоки должны быть **в середине** потока (не в
> конце) и **полноразмерными** (1024 сэмпла). Отсюда `--start-index 200 --count 3
> --min-step-ms 15`.

## Как фиксить (в Chromium)

`DiscardPadding` по спецификации **знаковое** целое. Отрицательное значение
означает «отбросить N сэмплов с начала блока». Правильная обработка:

1. Трактовать отрицательный `DiscardPadding` как отбрасывание сэмплов **в начале**
   блока, а не как отрицательную длительность.
2. Не давать ему влиять на длительность пакета / арифметику таймстемпов «в лоб».
3. Минимум — защита от немонотонных/переполненных значений.

## Матрица бисекции

| Файл | Изменение | Краш |
|------|-----------|------|
| `cat.webm` | оригинал (7.1) | да |
| + только `SeekHead`/`Cues` | индекс ни при чём | да |
| только Info/Tracks/Tags | не метаданные | да |
| только флаг блока 0x00→0x80 | не флаг | да |
| `BlockGroup` без `DiscardPadding` | padding виноват | нет |
| `BlockGroup`→`SimpleBlock`, padding убран | — | нет |
| без `CodecDelay`, с отриц. `DiscardPadding` | — | нет |
| с `CodecDelay`, без `DiscardPadding` | — | нет |
| с `CodecDelay`, с отриц. `DiscardPadding` (Vorbis) | **триггер** | **да** |
| тот же инжект на Opus | Vorbis-специфично | нет |
| отриц. `DiscardPadding` на микро-блоке (128 сэмплов) | нужен полноразмерный блок | нет |
| отриц. `DiscardPadding` на последнем блоке | нужна середина потока | нет |
